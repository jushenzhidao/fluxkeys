## 1. 概述

### 1.1 背景

- 火山引擎每日赠送 500 万 Token（大模型）+ 100 次（文生图等按次计费）
- 拥有 1000 个独立 Key，需实现智能调度
- 活跃 Key 约 100 个即可满足业务吞吐
- 火山商务反馈：封禁根因是**用户行为规律相似**
- 配额刷新时间：**每日 12:00-13:00**

### 1.2 设计目标

| 目标 | 指标 |
|------|------|
| 不超刷 | 硬水位线 + 预扣原子操作 |
| 留余量 | 软水位线降权，硬水位线拒绝 |
| 剩余量优先 | 调度分数与实时剩余配额正相关 |
| 跨日记忆 | 昨日低消耗 Key 今日获得额外权重 |
| 行为差异化 | 1000 个 Key 像 1000 个独立用户 |
| 零感知切换 | 401/403/429 自动换 Key，用户无感知 |
| 通用透传 | 用户侧 OpenAI 兼容，渠道差异内部消化 |
| 热更新 | 配置变更不停机，50ms 内生效 |
| 性能 | P99 调度延迟 < 2ms，单实例 QPS > 1000 |

### 1.3 核心约束

- **Token 型配额**: 500 万 Token/日，中午 12:00-13:00 刷新
- **次数型配额**: 100 次/日（如 Seedream），中午 12:00-13:00 刷新
- **单 Key RPM**: 500 次/分钟
- **单 Key TPM**: 100 万 Token/分钟
- **安心模式陷阱**: 免费额度耗尽后自动熔断，即使账户有余额也停服

## 4. 核心设计原则

| 原则 | 说明 |
|------|------|
| **用户侧零感知** | 用户永远用 OpenAI 兼容 API，换渠道商不用改代码 |
| **渠道差异内部消化** | 认证头、URL、响应格式差异在 Adapter 层处理 |
| **Key-IP 终身绑定** | 每个 Key 绑定固定出口 IP，不频繁切换 |
| **IP 不共享连接池** | 每个 Key 独立 Session，独立 TCP 连接 |
| **配置热更新** | 改 IP 绑定、路由规则不需要重启服务 |
| **故障自动切换** | Key 被封/IP 故障自动迁移，用户无感知 |
| **负载动态均衡** | 根据实际负载自动调整 Key 分布 |
| **渐进式扩容** | 从 5 个 IP 起步，按需增加 |
| **行为差异化** | 1000 个 Key 像 1000 个独立用户 |
| **不超刷** | 硬水位线 + 预扣原子操作 + 实时修正 |
| **跨日记忆** | 昨日低消耗 Key 今日优先调度 |
| **性能优先** | P99 调度 < 2ms，单实例 QPS > 1000 |

## 5. 详细架构

### 5.1 路由层

```
用户请求 URL: POST /v1/chat/completions

路由解析流程:
1. URL 匹配路由表
   /v1/chat/completions  →  upstream_path: /api/v3/chat/completions
                         →  billing_type: token
                         →  stream_support: true

2. 渠道路由
   - 请求头 X-Provider: volc → 走火山渠道
   - 无 X-Provider → 按 model 字段隐式映射
     deepseek-v3 → volc
     gpt-4       → openai (fallback)

3. 用户鉴权
   - 校验 Authorization: Bearer {user_key}
   - 检查用户配额/限流

4. 请求体解析
   - 提取 model 字段
   - 提取 max_tokens（用于预扣估算）
   - 提取 stream 字段
   - 保留完整 body 用于透传
```

### 5.2 调度核心层

```
调度核心 = 五维分数计算 + 加权随机采样

输入: 候选 Key 集合（已通过状态/配额/行为初筛）
输出: 选中的 Key + 绑定 IP + Session

处理流程:
1. 候选 Key 筛选
   - 状态 = active
   - 配额 < 硬水位线
   - 当前时间在活跃时段内
   - 与已选 Key 行为相似度 < 0.6

2. 五维分数计算
   Score = w1*S_quota + w2*S_history + w3*S_persona + w4*S_health - w5*P_watermark

3. 加权随机采样
   - 按分数分桶（180-200, 160-180...）
   - 桶内随机选择
   - 避免总是选最高分 Key

4. 预扣配额
   - Token 型: max_tokens * 1.5
   - 次数型: 1
   - 本地内存标记 + 异步刷 Redis

5. 获取 Session
   - 查 Key 绑定 IP
   - 获取/创建绑定该 IP 的 Session
   - 注入 Key 级指纹头
```

### 5.3 配额管理层

```
三级水位体系:

Token 型 (500万/日):
┌─────────────────────────────────────────┐
│  500万 │ 绝对上限（火山侧硬限制）          │
├─────────────────────────────────────────┤
│  450万 │ 硬水位线（系统拒绝，留50万缓冲）  │
├─────────────────────────────────────────┤
│  400万 │ 软水位线（权重降50%）            │
├─────────────────────────────────────────┤
│  0-400万 │ 正常调度区间                    │
└─────────────────────────────────────────┘

次数型 (100次/日):
┌─────────────────────────────────────────┐
│  100次 │ 绝对上限                         │
├─────────────────────────────────────────┤
│   90次 │ 硬水位线（留10次缓冲）            │
├─────────────────────────────────────────┤
│   80次 │ 软水位线（权重降50%）             │
├─────────────────────────────────────────┤
│  0-80次 │ 正常调度区间                     │
└─────────────────────────────────────────┘

本地缓存 + 异步刷盘:
┌─────────────────────────────────────────┐
│  内存配额表 (O(1)读写)                   │
│  ┌────────┬────────┬────────┬────────┐ │
│  │ KeyID  │ used   │ pre    │ dirty  │ │
│  ├────────┼────────┼────────┼────────┤ │
│  │ K001   │ 230万  │ 5万    │ false  │ │
│  │ K002   │ 180万  │ 3万    │ true   │ │
│  └────────┴────────┴────────┴────────┘ │
│                                         │
│  写: 先写内存，标记 dirty               │
│  读: 优先内存，miss 则读 Redis          │
│  刷盘: 100ms 或 1000 条批量 Pipeline    │
│  一致性: 内存 TTL 5s，过期强制读 Redis   │
│  多实例: Redis Pub/Sub 通知刷新          │
└─────────────────────────────────────────┘
```

### 5.4 IP 出口层

```
单服务器多 EIP 架构:

服务器 (4C8G, ¥200-300/月)
  ├─ eth0: 172.16.0.1 (管理流量)
  ├─ eth0:0  172.16.0.2 → EIP 1.2.3.4
  ├─ eth0:1  172.16.0.3 → EIP 1.2.3.5
  ├─ eth0:2  172.16.0.4 → EIP 1.2.3.6
  └─ ... 共 5-10 个辅助 IP

Key-IP 绑定:
  - 每个 Key 终身绑定 1 个主 IP
  - 20% Key 有备用 IP（故障切换后恢复）
  - 同一 IP 下绑 5-10 个 Key
  - 同一 IP 下的 Key 作息完全错开

分级连接池:
  活跃 Key (100个): 独立 Session，HTTP/2 多路复用，5-10 连接/Key
  预热 Key (200个): 共享连接池，2-3 连接/Key
  冷备 Key (700个): 无持久连接，临时创建
```

### 5.5 渠道适配层

```
通用入口 → 渠道路由 → Provider Adapter → 渠道特定请求

Adapter 接口:
  1. transform_request: 通用请求体 → 渠道请求体
  2. transform_response: 渠道响应体 → 通用响应体
  3. transform_stream_chunk: 渠道 SSE → 通用 SSE
  4. build_auth_headers: 渠道 Key → 认证头

  6. map_error: 渠道错误码 → 通用错误码

  - 认证: Authorization: Bearer {key}
  - Base: https://ark.cn-beijing.volces.com
  - 请求体: OpenAI 兼容，原样透传
  - 响应体: OpenAI 兼容，原样透传
  - Usage: 响应体 / 流式最后 chunk
  - 计费: Token + Count 双模式

未来扩展 (OpenAIAdapter / AnthropicAdapter / AzureAdapter):
  - 实现同样的 6 个接口
  - 用户侧零改动
  - 新增渠道 = 新增一个 Adapter 文件
```

## 7. 调度算法

### 7.1 五维分数公式

```
Score = w1 * S_quota + w2 * S_history + w3 * S_persona + w4 * S_health - w5 * P_watermark

权重配置:
  w1 = 35   // 实时剩余配额权重
  w2 = 25   // 跨日历史权重
  w3 = 20   // 行为匹配权重
  w4 = 15   // 健康度权重
  w5 = 惩罚系数 // 软水位时 = 20，硬水位直接淘汰
```

### 7.2 各维度计算

**S_quota (实时剩余配额分)**
```
剩余比例 = (硬水位 - 已用量) / 硬水位

S_quota = 剩余比例 * 100

特殊处理:
  剩余比例 > 0.5: 额外 +10 分鼓励使用
  0.2 < 剩余比例 <= 0.5: 正常计算
  剩余比例 <= 0.2: 进入紧张模式，-10 分
```

**S_history (跨日历史分)**
```
昨日余量比例 = 1 - yesterday_ratio

base_bonus = 昨日余量比例 * 25 分（满分 25）

consecutive_bonus = min(连续低消耗天数 * 3 分, 15 分)

昨日刷满惩罚（消耗率 > 95%）:
  S_history = -15 分

示例:
  Key A: 昨日消耗 450万(0.9), 连续 0 天低消耗 → 2.5 + 0 = 2.5 分
  Key B: 昨日消耗 200万(0.4), 连续 1 天低消耗 → 15 + 3 = 18 分
  Key C: 昨日消耗 50万(0.1), 连续 3 天低消耗 → 22.5 + 9 = 31.5 分
  Key D: 昨日消耗 500万(1.0) → -15 分（惩罚）
```

**S_persona (行为匹配分)**
```
S_persona = 100 * 行为匹配度

行为匹配度:
  - 当前时间在 Key 活跃时段内: 1.0，否则 0.0（直接淘汰）
  - 请求类型与 Key 画像偏好匹配度: 0.0-1.0
  - 今日已请求数是否符合工作模式预期
```

**S_health (健康度分)**
```
S_health = health_score

health_score 计算:
  基础分: 100
  连续 429: 每次 -10
  5xx 错误: 每次 -5
  请求超时: 每次 -3
  成功率 < 95%: 额外 -10
  每日衰减恢复: +5（最高 100）
```

**P_watermark (水位惩罚)**
```
已用量 >= 硬水位（450万 / 90次）:
  P_watermark = +∞（直接淘汰）

已用量 >= 软水位（400万 / 80次）:
  P_watermark = 20 分（大幅降权）
```

### 7.3 加权随机采样

```
传统方法: 计算所有分数 → 归一化 → 按概率随机选
问题: 每次遍历全部 Key

优化: 分数分桶采样

分数区间分桶（预计算）:
  Bucket 180-200: [K001, K015, K032]
  Bucket 160-180: [K002, K008, K045]
  Bucket 140-160: [K003, K012, K067]
  ...

采样时:
  1. 按桶权重随机选一个桶（高分数桶权重高）
  2. 在桶内随机选一个 Key
  3. 平均比较次数: 3-5 次（而不是 100 次）
```

### 7.4 调度延迟对比

| 方案 | 平均延迟 | P99 |
|------|---------|-----|
| 朴素遍历 | 2ms | 8ms |
| 全量预计算 | 0.5ms | 2ms |
| 分层缓存 + 分桶 | **0.2ms** | **1ms** |

### 8.1 配额刷新机制

```

错峰刷新策略:

刷新时序:
  12:00  批次1 (30%): 昨日消耗最快的 Key 优先刷新
  12:20  批次2 (40%): 标准错峰
  12:50  批次3 (30%): 昨日消耗慢的 Key 最后刷新

刷新后行为:
  - 前 30 分钟: 限速 50%（"起床缓冲"）
  - 30 分钟后: 正常调度

刷新前处理 (11:00-12:00):
  - 进入低功耗模式: 仅短问答 (<500 tokens)
  - 关闭流式、关闭思考模式
  - RPM 降至平时 30%
  - 11:30 启动预刷新预热: 从冷备池选 5-10 个 Key 提前激活
```

### 8.2 预扣与修正

```
请求前预扣（Lua 原子操作）:
  available = hard_limit - used - prededuct
  if available >= request_estimate:
      prededuct += request_estimate
      return OK
  else:
      return INSUFFICIENT

请求后修正（异步）:
  actual = response.usage.total_tokens
  used += actual
  prededuct -= request_estimate

  // 差额处理（保守策略）:
  // prededuct 释放，used 按 actual 累计
  // 不扣回 used（防止并发下超刷）

流式请求特殊处理:
  - 请求前: 按 max_tokens 预扣
  - 流式过程中: 内存累加预估 Token，不写 Redis
  - 流式结束: 解析最后 chunk 的 usage，一次性修正
  - 优势: Redis 写次数从 N chunks 降到 1 次
```

### 10.2 Key-IP 绑定规则

```
绑定算法:
  primary_hash = hash(key_id + "primary_ip_salt") % len(ip_pool)
  primary_ip = ip_pool[primary_hash]

  20% 的 Key 分配备用 IP:
    if hash(key_id + "backup_flag") % 100 < 20:
        backup_hash = (primary_hash + hash(key_id) % 5 + 1) % len(ip_pool)
        backup_ip = ip_pool[backup_hash]
        return [primary_ip, backup_ip]
    return [primary_ip]

使用规则:
  正常请求: 主 IP（90%）
  主 IP 故障: 备用 IP（10%）
  429 限流: 主 IP + 指数退避，不切换 IP
  保活心跳: 主 IP
  紧急晋升: 主 IP

绝对禁止:
  - 同一个请求同时走多个 IP
  - 同一个 Key 在 1 小时内切换 IP
  - 按 Round-Robin 轮询 IP
```

### 10.3 单 IP 多 Key 的安全策略

```
一个 IP 绑 10 个 Key，如何不暴露?

1. 作息完全错开
   IP_1 下的 10 个 Key:
     Key_001: 08:00-12:00 活跃
     Key_002: 10:00-14:00 活跃
     Key_003: 14:00-18:00 活跃
     Key_004: 20:00-24:00 活跃
     Key_005: 00:00-04:00 活跃（夜猫子）
     ...
   同一时刻，该 IP 下只有 2-3 个 Key 在活跃

2. 请求间隔分散
   每个 Key 的请求间隔 > 5 秒
   同一 IP 下并发请求 < 3 个

3. 行为差异化
   同一 IP 下的 Key 使用不同模型、不同长度、不同温度
   避免"同一 IP 发出相似请求"的模式
```

### 10.4 IP 健康检查

```
    "stream": true,
    "max_tokens": 4096,
    "temperature": 0.7
  }
```

### 11.2 渠道路由优先级

```
1. 请求头 X-Provider
   例: X-Provider: volc → 只从火山 Key 池选

2. 模型名隐式映射
   例: model=deepseek-v3 → 火山
       model=gpt-4 → OpenAI
       model=claude-3-5 → Anthropic

3. 用户配置默认渠道
   例: 用户 A 配置默认走火山

4. 智能路由 (fallback)
   例: 火山配额耗尽 → 自动 fallback 到 OpenAI（同模型或近似模型）
```

### 11.3 Adapter 接口

```
每个渠道商实现统一的 Adapter 接口:

1. transform_request
   输入: 通用请求体（OpenAI 格式）
   输出: 渠道商特定请求体

2. transform_response
   输入: 渠道商响应体
   输出: 通用响应体（OpenAI 格式，包含 usage）

3. transform_stream_chunk
   输入: 渠道商 SSE chunk
   输出: 通用 SSE chunk（OpenAI 格式）

4. build_auth_headers
   输入: 渠道 Key
   输出: 认证头字典

5. parse_usage
   输入: 响应体 / 流式最后 chunk
   输出: {prompt_tokens, completion_tokens, total_tokens}

6. map_error
   输入: 渠道商状态码 + 响应体
   输出: 通用错误码 + 通用错误体
```

```
计费:
  Token 型: 500万/日
  次数型: 100次/日（如 Seedream）

错误码映射:
  401 → Key 无效/过期 → 禁用 Key
  403 → 权限不足/被封 → 禁用 Key，人工队列
  404 → 模型不存在 → 直接透传
  429 → 速率限制 → Key 冷却，指数退避
  500+ → 服务端错误 → 换 Key 重试
```

## 12. 性能优化

### 12.1 调度路径优化

```
分层缓存架构:

Layer 1: 全量预计算分数表（每 5 秒刷新）
  KeyID │ S_quota │ S_history │ S_persona │ Total
  ──────┼─────────┼───────────┼───────────┼───────
  K001  │   87    │    25     │    90     │  202
  K002  │   65    │    10     │    85     │  160
  ...

Layer 2: 实时修正层（每次请求后更新）
  - token_used 变化 → S_quota 实时修正
  - 健康度变化 → S_health 实时修正
  - 其他维度变化频率低，依赖 Layer 1 刷新

Layer 3: 候选 Key 快速筛选（位图）
  - 用 bitmap 标记"当前可调度"的 Key
  - 非活跃时段的 Key 直接 bitmap 置 0
```

### 12.2 Redis 优化

```
本地缓存 + 异步刷盘:

内存配额表（O(1) 读写）:
  KeyID │ used    │ prededuct │ dirty
  ──────┼─────────┼───────────┼───────
  K001  │ 2300000 │   50000   │ false
  K002  │ 1800000 │   30000   │ true

写策略:
  - 预扣: 先写内存，标记 dirty，异步批量刷 Redis
  - 修正: 先写内存，标记 dirty，异步批量刷 Redis
  - 批量间隔: 100ms 或 1000 条（先到先触发）

读策略:
  - 优先读内存（O(1)）
  - 内存 miss → 读 Redis → 回填内存
  - 启动时全量预热: 从 Redis 加载所有 Key 配额到内存

一致性保证:
  - 内存数据 TTL: 5 秒，过期强制读 Redis
  - 脏数据刷盘: 批量 Pipeline，失败回退单条重试
  - 多实例同步: Redis Pub/Sub 通知其他实例刷新
```

### 12.3 连接池优化

```
分级连接池架构:

Tier 1: 活跃 Key 连接池（100 个 Key）
  - 每个 Key 独立 Session
  - 连接池大小: 5-10 个（根据该 Key 的 QPS 动态调整）
  - KeepAlive: 60 秒
  - 空闲超时: 120 秒（超过关闭，下次请求重建）

Tier 2: 预热 Key 连接池（200 个 Key）
  - 共享连接池（按 IP 分组）
  - 连接池大小: 2-3 个/Key
  - KeepAlive: 30 秒
  - 空闲超时: 60 秒

Tier 3: 冷备 Key（700 个 Key）
  - 无持久连接
  - 需要时临时创建，用完即关
  - 保活心跳: 每 3-5 天 1 次，临时连接

HTTP/2 多路复用:
  - 同一 IP 下的多个 Key 共享底层 TCP 连接
  - 一个 TCP 连接可以并发多个请求（不同 Stream）
  - 流式请求仍建议独立连接（避免阻塞）
```

### 12.4 流式请求优化

```
异步流式处理（Python asyncio / Go goroutine）:

Python:
  async def stream_request(key_id, req):
      session = get_async_session(key_id)
      async with session.post(...) as resp:
          async for chunk in resp.content:
              yield chunk

Go:
  func streamRequest(keyID string, req Request) {
      resp, _ := client.Post(...)
      defer resp.Body.Close()
      scanner := bufio.NewScanner(resp.Body)
      for scanner.Scan() {
          chunk := scanner.Bytes()
          sendToUser(chunk)
      }
  }

配额修正策略:
  - 请求前: 按 max_tokens 预扣
  - 流式过程中: 内存累加，不写 Redis
  - 流式结束: 解析 usage.total_tokens，一次性修正
  - 优势: Redis 写次数从 N chunks 降到 1 次
```

### 12.5 热更新零停顿

```
RCU（Read-Copy-Update）模式:

内存结构:
  key_sessions (原子指针)
    ├─ 指向 SessionMap_A (当前生效)
    └─ 更新时: 创建 SessionMap_B → CAS 替换指针

读操作（请求路径）:
  1. 原子读取当前指针 → 得到 SessionMap_A
  2. 在 Map_A 中查找 Key 的 Session
  3. 发请求（全程无锁）

写操作（配置变更）:
  1. 复制 SessionMap_A → SessionMap_B
  2. 在 Map_B 中修改 Key_001 的绑定 IP
  3. 创建新的 Session（绑定新 IP）
  4. CAS 原子替换指针: key_sessions = Map_B
  5. 旧 Map_A 标记为"退役"，延迟 5 秒后释放

效果:
  - 读操作永远无锁、无阻塞
  - 写操作通过 CAS 保证原子性
  - 旧 Session 延迟释放，保证正在进行的请求完成

配置变更批量化:
  - 收集一批变更（100ms 窗口内）
  - 生成新版本号（version += 1）
  - 复制全量 Map → 应用所有变更 → CAS 替换
  - 单次 CAS 完成批量更新
  - 平均延迟 < 1ms
```

### 12.6 性能基准

| 指标 | 目标值 | 说明 |
|------|--------|------|
| P99 调度延迟 | < 2ms | 分层缓存 + 分桶采样 |
| P99 预扣延迟 | < 1ms | 本地缓存 + 异步刷盘 |
| 单实例 QPS | > 1000 | 4 核 8G |
| 流式并发 | > 500 | 协程/异步 IO |
| 内存占用 | < 500MB | 分级连接池 + 本地缓存 |
| 配置热更新 | < 50ms | RCU 无锁切换 |

## 13. 错误处理与重试

### 13.1 错误码处理矩阵

| 上游状态码 | 含义 | 透传给用户 | 内部处理 | 用户感知 |
|-----------|------|-----------|---------|---------|
| 200 | 成功 | 原样 | 修正配额 | 正常响应 |
| 400 | 参数错误 | 原样 | 记录日志 | 参数错误 |
| 401 | Key 无效/过期 | 原样 | 禁用 Key，候补晋升 | 内部重试后仍失败则透传 |
| 403 | 权限不足/被封 | 原样 | 禁用 Key，人工队列 | 同上 |
| 404 | 模型不存在 | 原样 | 记录，不换 Key | 模型不存在 |
| 429 | 速率限制 | 可替换为 503 | Key 冷却，换 Key 重试 | 无感知或超时 |
| 500 | 服务端错误 | 原样 | 换 Key 重试（最多 3 次） | 无感知或最终透传 |
| 502/503 | 网关错误 | 原样 | 换 Key 重试 | 无感知或最终透传 |
| 504 | 超时 | 原样 | 换 Key 重试 | 无感知或最终透传 |

### 13.2 自动重试策略

```
收到错误响应后的处理:

1. 解析状态码
    │
    ├──▶ 401/403
    │    - 立即禁用该 Key
    │    - 从活跃池移除
    │    - 触发候补 Key 晋升
    │    - 用新 Key 重试（用户无感知）
    │    - 最多重试 3 个不同 Key
    │    - 如果都失败 → 透传最后一个错误给用户
    │
    ├──▶ 429
    │    - 该 Key 进入冷却（指数退避: 1s, 2s, 4s...）
    │    - 标记"临时不可用"
    │    - 换其他 Key 重试
    │    - 如果所有 Key 都 429 → 返回 503"服务繁忙"
    │
    ├──▶ 404
    │    - 不换 Key，直接透传
    │    - 用户传的模型不存在，换 Key 也没用
    │
    └──▶ 5xx/超时
         - 换 Key 重试（最多 3 次）
         - 如果都失败 → 透传最后一个错误
```

### 13.3 Key 状态机

```
                    ┌─────────────┐
         ┌─────────▶│   active    │◀────────┐
         │          │   (活跃)     │         │
         │          └──────┬──────┘         │
         │                 │                 │
    配额耗尽/轮换          各种错误           冷却结束
         │                 │                 │
         ▼                 ▼                 │
    ┌─────────┐      ┌──────────┐            │
    │  cold   │      │ cooldown │────────────┘
    │ (冷备)   │      │ (冷却中)  │
```
